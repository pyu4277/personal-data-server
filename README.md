# 개인 데이터 서버 — CGNAT 뒤에서 만든 홈 서버

여러 PC가 같은 데이터를 쓰고 집 밖에서도 접속되는 개인 서버를 만든 기록과, 그 결과물.
Google Drive 의존을 끊고 본인 NVMe에 데이터를 두는 것이 출발점이었다.

> **이 저장소는 비공개다.** 집 네트워크 구성, 공인 IP, tailnet 이름 같은 식별 정보가
> 문서에 들어 있다. 비밀번호는 어디에도 없다 — 서버 PC의
> `C:\ProgramData\HomeDataServer\credentials.txt` 에만 있고 저장소에는 담지 않았다.

---

## 무엇을 만들었나

| 경로 | 수단 |
|---|---|
| 웹 UI · 모바일 포함 | SFTPGo + Tailscale Serve · Let's Encrypt 정식 인증서 |
| 탐색기 드라이브 | SMB + 전용 로컬 계정 |
| WebDAV | HTTPS |
| 집 안 기기 전체 | Tailscale 서브넷 라우터 |
| 공유기 관리 페이지 | Serve 프록시로 HTTPS 우회 |

데이터 루트는 `D:\` 드라이브 전체. 외부 클라우드를 거치지 않고, 본인 계정의 기기만 접근한다.

## 왜 공유기가 아니라 Tailscale인가

가장 자연스러운 출발점은 공유기 포트포워딩이었다. 그런데 공유기에게 자기 WAN 주소를
물었더니 **사설 주소**가 돌아왔다.

```
공유기가 보고하는 WAN IP   10.123.216.73    ← 사설 (RFC1918)
인터넷에서 본 공인 IP       220.67.182.216
```

둘이 다르다는 건 공유기 위에 **통신사 NAT(CGNAT)** 가 한 겹 더 있다는 뜻이다.
포트포워딩 규칙은 "내 공유기에 도착한 패킷"을 다루는데, 그 패킷이 애초에 도착하지 못한다.

그래서 인바운드를 받는 방식은 전부 탈락했다 — 포트포워딩, DDNS,
공유기의 WireGuard/PPTP/L2TP **서버**, ipDISK. ipTIME AX6000M이 이 기능들을 실제로
갖추고 있었지만, 전부 "공인 IP + 인바운드 개방"을 전제로 설계된 것들이다.

남은 방식은 **안에서 밖으로 나가는 터널**뿐이었고, 그중 Tailscale이
이미 6대에 설치돼 직결로 동작하고 있었다. 자세한 비교는 여정 문서의 `왜 Tailscale인가` 참조.

## 저장소 구성

```
docs/journey.html          여정 전체 기록 (인터랙티브 단일 HTML)
client-setup/              다른 PC를 연결하는 배포본
_orchestration/            구축 당시 에이전트들의 산출물
```

### `docs/journey.html`

브라우저로 열면 되는 단일 파일. 메뉴로 나뉘어 있고 항목을 누르면 곁창이 열린다.

- **결함 기록 19건** — 무엇이 왜 깨졌는지, 원인과 수정
- **폐기된 선택지 12개** — 검토했지만 채택하지 않은 것들과 그 사유
- **왜 Tailscale인가** — 결정 트리와 후보 비교
- **오케스트레이션** — 3개 모델 7개 에이전트가 무엇을 했는지
- **원문 보기** — 세션 대화 전문 45턴 (목록 / 전체 이어보기)
- 서브 AI로 작업을 보낸 지점(→)과 돌아온 지점(←) 표기, 클릭하면 그 AI의 지시·보고 원문

비밀번호는 마스킹했고, 초반 콘솔 인코딩이 깨진 자리는 `?` 로 표기했다.

### `client-setup/`

다른 Windows PC에서 이 서버를 드라이브로 연결하는 배포본. **v2.0**

```
개인서버 연결하기.bat        더블클릭 (관리자 승격 자동)
개인서버 연결끊기.bat        되돌리기
Connect-PersonalServer.ps1  본체
사용법.md                    상세 안내
```

전제는 그 PC에 Tailscale이 설치·로그인돼 있을 것. 자세한 내용은 `client-setup/사용법.md`.

## 이 프로젝트에서 남길 만한 것

- **측정이 일반론을 이긴다.** "KT는 보통 CGNAT를 안 쓴다"는 진술이 공유기 UPnP 한 번의
  호출로 무너졌다. 설계를 좌우하는 전제는 그 환경에서 직접 확인할 것.
- **로그의 타임스탬프도 정보다.** 내용이 아니라 "갱신되지 않았다"는 사실이 크래시 지점을 알려줬다.
- **진단 도구를 먼저 의심할 것.** PowerShell 함수에서 `Write-Output` 으로 로깅하면
  반환값이 오염된다. 도구가 거짓 성공을 보고하는 동안 진짜 원인은 가려져 있었다.
- **권한 강화는 잠금 위험 없는 방향으로.** 상속을 끊고 권한을 대체하면 관리자까지 잠긴다.
- **순서를 바꾸면 결함이 사라진다.** '연결 → 이름변경 → 재연결'을 '이름등록 → 연결'로
  바꾸자 재연결 단계와 그로 인한 오류가 함께 없어졌다.
- **한글 PowerShell 스크립트는 BOM 있는 UTF-8.** 없으면 PS 5.1이 ANSI로 읽어 파서가 깨진다.

전체 목록은 여정 문서의 `교훈` 참조.
